# Phase 2.2 — Independently linked native modeling-core extraction

**Status: active. Native independent BMesh build and Phase 2.2.2 pinned-source Blender geometry reference parity PASSED. General-purpose extraction, UV/attribute parity and Phase 2.3 stabilization remain outstanding.**
**Development branch:** `dev/p2-core-extraction` (based on the merged `blender-for-web` Phase 1.3 integration branch).
**Original Blender source baseline:** 5.4 Alpha, `67e5a5f874cf37e2a114cebd24f219d8c44a16ad`.
**Policy:** non-destructive, opt-in, keep `main` pristine, no unsupported full Blender build claims.

## What is being extracted

A new standalone CMake project in `tools/blender_web/native_core/` compiles original Blender implementation files **outside the desktop Blender application build graph**, producing `libblender_web_native_core.so` and a separate native test executable. Its source manifest is explicit (not a blanket `source/blender` glob).

The starting closure reuses the known-passing Emscripten experimental source set from Phase 1.3:
- 41 original Blender implementation translation units across BMesh, BLI, BKE, guardedalloc and CLog;
- one separate C ABI bridge (`tools/blender_web/wasm/bmesh_handle_api.cc`);
- one native smoke/stress test TU (`native_core_smoke.cc`).

The C ABI uses generation-tagged integer handles and bounded cube creation, original Blender discrete face extrusion, correct BMesh destruction, basic topological validity checks, and position/triangle snapshots copied into caller-owned buffers. This is a **narrow experimental modeling core**, not all of Blender's BKE/Geometry systems, nor the final general-purpose modeling library.

`CMakeLists.txt` explicitly links a shared library with `--no-undefined` and function-section GC (Linux). It needs a native C++20 compiler, CMake, Ninja, `fmt` headers and standard threading libraries, **not a completed full Blender CMake configuration**.

## Verified native CI evidence

**Passing workflow:** https://github.com/bhargavkalita47/blender/actions/runs/42389302741

On the pinned Blender 5.4 Alpha fork, Clang successfully compiled all 41 original Blender translation units, created `libblender_web_native_core.so` with `--no-undefined`, linked a standalone native executable, and passed CTest and the direct smoke test. The executable ran **1,000** full cube / original Blender BMO extrusion twice / mesh export / free cycles, yielding **2,000** original BMO extrusions. After every 100 cycles, the GuardedAlloc bytes returned to the warmed baseline, and zero mesh handles remained live.

The source and dynamic-library audit also passed. There were no selected GHOST/GPU/Draw/WindowManager/Render source translation units and no unexpected native UI/renderer unresolved symbols. Reported runtime libraries were only the standard Linux loader, libc, libgcc_s, libm and libstdc++.

**Earlier failure resolved:** the first workflow's native linker failure was masked by a `tee` pipeline. We corrected the workflow to use `set -o pipefail` and restricted native source visibility so that unrelated Blender functions and their dependencies can be eliminated at link time. The corrected, enforced workflow passed. Neither an incomplete link nor a missing test binary is considered success.

**Workflow:** `.github/workflows/blender-web-p2-2-native-core.yml`

It must:
1. Configure the standalone CMake target without invoking Blender's upstream application CMake.
2. Build and link the original source-backed shared modeling library with no unresolved link symbols.
3. Execute actual C ABI tests through a separate native executable: construct cube (8V/12E/6F/24L), extrude top face twice using original BMO, snapshot positions and triangle indices, validate topology, reject invalid or stale handles, destroy allocated data.
4. Repeat 1,000 create/edit/edit/export/free cycles; assert no net GuardedAlloc-tracked memory after warmup and no live mesh handles.
5. Analyze `compile_commands.json` and dynamic shared-library symbols/dependencies to reject native GHOST, GPU, Draw, WM, Render source units or unexpected linked desktop/graphics dependencies.
6. Upload logs, compile command manifest, isolation report, built library and executable.

**The first independent native BMesh target has passed its narrow acceptance gate; this is not complete Phase 2.2 native modeling extraction.** The current configuration deliberately uses the same `-funsigned-char`, `FMT_HEADER_ONLY`, `BLENDER_WEB_MINIMAL_BMO` compatibility flags as the already verified WASM experiment; serialized DNA compatibility is **not** proven by this profile.

## Prior Phase 2 materials retained

The earlier `dev/p2-extraction` draft provided two useful, non-destructive tools. They are preserved here:
- `tools/blender_web/cmake/modeling-headless.cmake`: reversible opt-in native **full Blender** diagnostic profile. Not the extracted-core target.
- `tools/blender_web/tests/native_reference.py`: original Blender 5.4 BMesh cube, UV, extrude and triangulation reference script. Running it requires a compatible **full native Blender binary** and dependencies.

The Phase 2.3 regression/acceptance plan is retained separately. No source directories have been deleted.

## Reproduction (native Linux, from repo root)

```sh
sudo apt-get install clang ninja-build libfmt-dev binutils
cmake -S tools/blender_web/native_core \
  -B build/blender_web/native_core -G Ninja \
  -DCMAKE_CXX_COMPILER=clang++ -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build/blender_web/native_core --parallel 4
ctest --test-dir build/blender_web/native_core --output-on-failure
python3 tools/blender_web/native_core/verify_build_isolation.py \
  build/blender_web/native_core
```

The native shared library is *not* compiled with Emscripten; the full JavaScript-facing WebAssembly implementation remains in Phase 1.3.

### Known blocker

The previous **full Blender** CMake configuration is still blocked by unavailable compatible OpenColorIO 2.3.0 development resources in its CI environment. The 2.2.2 geometry reference gate instead uses the official Blender 5.4 Alpha binary with a strictly verified matching build hash `67e5a5f874cf`. This standalone CMake experiment is designed to avoid requiring an entire native desktop Blender build as a prerequisite for **isolated** BMesh linking. It does not magically fix the outstanding full native configuration or the original Blender reference test.

**Exit gate for Phase 2.2** remains an independently compiled native modeling core with verified behavior against the native source baseline. A successful minimal cube experiment would be an important sub-gate, **not all of Phase 2.2**.
