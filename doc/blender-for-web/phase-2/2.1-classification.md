# Phase 2.1 — Component classification and reduction policy

**Status:** Classification complete as a proposed engineering disposition. **Code removal:** none. **Baseline:** Blender 5.4 Alpha, commit `67e5a5f874cf37e2a114cebd24f219d8c44a16ad`.

This classification follows [Phase 1.1 Architecture](../phase-1/1.1-architecture.md) and the [initial Phase 1.2 dependency ledger](../phase-1/1.2-dependencies.md). Phase 1.2's source-level closure and Phase 1.3 feasibility builds remain outstanding. Thus **the classifications below are not proof that a target can already be excluded or linked independently.**

## Policy: keep, isolate, replace, exclude

- **KEEP (engine):** Retain the necessary original Blender C/C++ algorithms/data structures. Preserve GPL notices, topology semantics, correct attribute storage and evaluated output.
- **ISOLATE:** Retain only required source/target portions, separating unrelated functionality at build boundaries. Do not remove individual source files unless compile/link and behavior validation show it is safe.
- **REPLACE (platform/presentation):** Replace native UI, input, windows or graphics with browser-specific adapters, without rewriting BMesh editing algorithms in JavaScript.
- **EXCLUDE FROM INITIAL WEB BUILD:** Omit from the web build when tested, but leave original source in Git. Do not conflate a feature omission with deletion of every supporting library.
- **DEFER DECISION:** Source closure/product requirements must be resolved before inclusion/exclusion.

## Initial product contract

### Core requirements (must not silently regress)

1. Scene with several mesh objects and basic transforms.
2. Primitive construction (cube, plane, cylinder, sphere).
3. Object and Edit modes, vertex/edge/face selection.
4. Mesh topology editing: extrude, inset, bevel, dissolve, merge and loop cut, progressively.
5. Correct face normals, triangulation and geometry attribute updates.
6. UV coordinates and an interactive UV editing workflow, at least with basic unwrap/assignment.
7. Basic material assignment and texture preview; avoid full offline rendering requirements.
8. Undo/redo, import/export and local project persistence.
9. Deterministic mesh buffer output usable by a browser renderer.
10. A well-defined native/WASM API that does not export unstable raw C++ object pointers.

The exact initial file formats, sculpt/paint capabilities, full modifier support and advanced procedural modeling are **not yet finalized**; treat them as deferred decisions, not already removed features.

**Feature classification is separate from linker feasibility.** For example, BKE's CMake target links Render, GHOST and Blender Loader; marking native rendering/windowing as excluded does not make those edges disappear.

## Non-destructive reduction rules

1. **Do not delete upstream directories in Phase 2.2.** Use opt-in build targets, generated manifests or configuration guards and retain reversible Git history.
2. Every excluded module must have an evidence record identifying the removed target edge and test results.
3. Preserve the original `main` fork and commit; all web modifications go through dev branches into `blender-for-web`.
4. No broad `#ifdef WEB` added to unrelated Blender code without documenting the portable interface being extracted.
5. Keep the native blender application build possible by making reduction tooling opt-in and default OFF until verified.
6. Do not merge partially working C++ extraction or claim a native test passed without an actual compile-and-run log.
7. Do not skip license notices or assume Blender GPL disappears because the UI is browser-based.
