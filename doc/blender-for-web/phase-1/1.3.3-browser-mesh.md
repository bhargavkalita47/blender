# Phase 1.3.3 — Browser-hosted Blender BMesh and JavaScript mesh-data transfer

**Status:** PASS; evidence from real browser engines.
**Original source:** pinned Blender 5.4 Alpha commit `67e5a5f874cf37e2a114cebd24f219d8c44a16ad`.
**Toolchain:** Emscripten 4.0.12, Node 22, Playwright 1.55.0.

## Verified run

https://github.com/bhargavkalita47/blender/actions/runs/42386157400

The CI workflow built original Blender BMesh into a 109,908-byte WASM module with a generated ES module loader, executed the engine in Node and then exercised it in **headless real Chromium and Firefox** browser processes. All steps passed. It created an 8-vertex cube, performed two original Blender BMO face extrusions, and transferred the final 16 vertices and 84 triangle index values to JavaScript. Browser geometry outputs were byte-for-byte equivalent as normal JavaScript number arrays. Both browsers passed 50 consecutive edit/export/destroy cycles and tracked Blender allocation returned to its warmed baseline.

A later Phase 1.3.4 run extends the same browser test to WebKit.

## Mesh transfer contract

`tools/blender_web/wasm/bmesh_handle_api.cc` exports the following bounded copy APIs in addition to generation-checked opaque mesh handles:

- `web_mesh_position_float_count`: expected position-float capacity;
- `web_mesh_triangle_index_count`: expected triangle-index capacity;
- `web_mesh_copy_positions`: write the original Blender vertex coordinates to caller-owned memory;
- `web_mesh_copy_triangles`: emit two triangles per *quad* Blender face into caller-owned memory.

The lightweight `mesh_buffers.mjs` adapter allocates **temporary** WASM scratch memory, copies the mesh geometry, produces independent `Float32Array` and `Uint32Array` copies, validates index bounds/finite coordinates, and releases both scratch buffers in `finally`. It never exposes a `BMVert`, `BMEdge` or `BMFace` pointer to application JavaScript. Memory views are read after allocation because WASM heap growth may detach previous typed-array views.

The initial triangulation is deliberately limited to the convex quad faces of the cube/extrusion fixture. It is **not** a verified general Blender polygon triangulator; n-gons, concave faces and arbitrary meshes need real geometry triangulation before viewport rendering.

## Acceptance evidence

- [x] Compile and link real Blender BMesh with the Emscripten browser+Node target.
- [x] Import the ES module and instantiate WASM in real browsers over HTTP with `application/wasm` MIME.
- [x] Create cube, perform original BMesh extrusions and check topology in browser.
- [x] Transfer actual vertex positions and triangle indices into JS typed arrays without exposing raw Blender element pointers.
- [x] Verify identical output in Chromium and Firefox and reject stale handles.
- [x] Recover tracked Blender allocations after repeated browser edits and exports.

## Out of scope

No interactive viewport, GPU/WebGL or WebGPU rendering, complex scene, UV editing, texturing, arbitrary n-gons or .blend serialization has yet been implemented. This is engine/data transfer feasibility, not a deployable browser 3D editor.
