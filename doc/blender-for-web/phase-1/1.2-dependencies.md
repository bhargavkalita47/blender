## Evidence levels — don't confuse them

- **Level A: direct CMake target edge.** A target appears in `set(LIB ...)`, `list(APPEND LIB ...)` or `target_link_libraries`. May be `PUBLIC`, `PRIVATE`, unconditional, conditional or platform-only.
- **Level B: transitive target edge.** A chain of Level A edges. It is *not* proof that one operation requires every target along the chain.
- **Level C: source dependency.** A concrete `#include`, referenced symbol, generated header or initialization requirement in a specific file.
- **Level D: required runtime dependency.** Proven by building, linking and exercising the selected operation. **No Level D verification yet.**

Note: Blender's `build_files/cmake/macros.cmake` implements `blender_link_libraries`, defaulting unspecified links to `PRIVATE`, and explicitly sets `LINK_INTERFACE_MULTIPLICITY 3` to handle longer link loops. An unqualified dependency below does not imply `PUBLIC`.

### Public and propagated dependencies worth investigating

- `bf_blenlib` declares DNA, intern profile, fmt, optional TBB and OpenImageIO with `PUBLIC` visibility.
- `bf_blenkernel` declares intern profile and optional OpenVDB `PUBLIC`; BKE comments that public headers contain OpenVDB items.
- `bf_blenloader` declares `bf::blenloader_core` `PUBLIC`.
- `bf_gpu` additionally `PUBLIC`-links generated shader libraries (`bf_compositor_shaders`, `bf_draw_shaders`, `bf_gpu_shaders`, `bf_imbuf_opencolorio_shaders`).

Those public interfaces are important because even seemingly unused functionality may be propagated to consumers of the original targets.

### Source closure worksheet to fill next

For each seed above, trace:

1. Direct project headers, system headers and generated headers.
2. Symbol definitions and the minimum object files that provide them.
3. Static/global initialization and shutdown prerequisites.
4. Runtime allocation, threading, file, GPU and OS calls.
5. Transitive code needed specifically for a successful native link.
6. Optional features that can be conditioned out.
7. Emscripten/browser substitution needed, if any.

## 4. Generated files and build-time executables

Blender's `source/blender/makesdna/intern/CMakeLists.txt` builds `makesdna`, emits generated data with `add_custom_command`, and defines `bf_dna` and related targets.

`source/blender/makesrna/intern/CMakeLists.txt` builds `makesrna` and uses a generated-code command; `bf_blenkernel` explicitly depends on `bf_rna`.

The GPU CMake target generates source-list and shader-metadata headers, and links several shader libraries publicly.

**Distinguish two cases:** A source file may depend on *generated headers during compilation* without requiring the runtime feature that originally motivated those headers. Conversely, dropping an executable code-generator without replacing its outputs can break an otherwise valid subset.

## 5. Platform and third-party decision ledger

| Area | Present mechanism | Proposed test in 1.2 / 1.3 |
| --- | --- | --- |
| Allocator | guardedalloc, BLI containers | Native and WASM allocation / lifetime smoke test |
| Threading | BLI threading, optional TBB, atomic, CMake platform libraries | Single-threaded first; identify actual source assumptions |
| Precision and geometry | Eigen, optional GMP, optional Manifold | Test simple primitives before complex Boolean algorithms |
| Compression | zlib, zstd | Defer until chosen persistence path requires them |
| Imaging | OpenImageIO, OpenEXR, JPEG, OpenColorIO | Distinguish essential textures from desktop render/color pipeline |
| Graphics | OpenGL, Vulkan, Metal, dummy backend | Decouple first WASM geometry proof from native GPU |
| OS services | GHOST, native filesystem/paths/process | Prefer browser adapters for services required by chosen sources |
| Codegen | DNA, RNA, shader metadata | Inventory exact generated artifacts and downstream headers |
| Source ABI | C++ classes/headers, runtime ownership | Start a stable opaque-handle C ABI, not raw C++ objects in JS |
