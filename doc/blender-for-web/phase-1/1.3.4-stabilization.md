These numbers are **specific to a tiny cube and two discrete-face extrusions on this particular CI runner**. They cannot be used as a meaningful Blender-versus-web benchmark, rendering FPS estimate, mobile-device estimate, or complex-scene performance claim. The 0-byte final guarded allocation demonstrates no net accounting imbalance under the tested workload, not a universal guarantee against all memory bugs. The C ABI has bounded 16-mesh slots and small quad-only fixture geometry.

### Required validation gates

- [x] Link and execute original BMesh create, edit, and free APIs and reject stale handles.
- [x] Repeated allocation, operator execution, indexed-geometry copying, and explicit destruction.
- [x] Track zero live meshes and no net Blender-accounted allocation after warmup.
- [x] Measure WASM heap growth and enforce a generous bound on this fixed workload.
- [x] Record benchmark latency, throughput, P95 and test conditions as CI artifact.
- [x] Execute in Chromium, Firefox and WebKit with identical mesh outputs.
- [x] Preserve original Blender `main` baseline unmodified.

## Remaining risks and Phase 2 prerequisites

1. There is still **no successful native full Blender CMake configuration** for the pinned alpha baseline due to the OpenColorIO 2.3.0 development-package requirement. The real native reduced modeling-core extraction and native/reference equivalence gates remain open.
2. No ASan/UBSan browser memory instrumentation, long-session production memory tracing or arbitrary topology fuzzing. GuardedAlloc and handle validation are the current experimental checks.
3. We have no representative scene, material, UV, undo, import/export, mobile device matrix or graphics viewport benchmarks. The final application must define performance budgets from real workloads.
4. `-funsigned-char` makes the selected wasm32 enum flags represent bit 7; this does not yet prove serialized Blender DNA compatibility.

**Milestone decision:** Phase 1.3.1–1.3.4 *isolated WebAssembly feasibility* tests pass. This is enough to proceed with planned Phase 2 work, while carrying the missing native CMake closure as an explicit, unresolved dependency. It is not a claim of production readiness or of a buildable extracted native core.
