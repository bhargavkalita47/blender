# Phase 1.1 — Architecture and feature mapping

**Status:** Architecture mapping deliverable complete. **Source:** Blender 5.4 Alpha; pinned reference `67e5a5f874cf37e2a114cebd24f219d8c44a16ad`.

**Method:** Read-only inspection of the checked-in source layout, subsystem CMake files, headers and representative entry points/flows. The purpose of 1.1 is to understand responsibilities and define a *working* product boundary; exhaustive transitive closure and compilability belong to 1.2 and 1.3.

## 1. Scope of the web application

The confirmed high-level intent is a **Blender-derived browser modeling, texturing and editing tool** that retains meaningful C/C++ Blender modeling algorithms rather than re-creating them entirely in JavaScript. The following is a **working feature map**, not an approved final UX specification.

| Capability | Initial disposition | Main Blender areas | Boundary / unresolved details |
| --- | --- | --- | --- |
| Mesh primitives (cube, plane, cylinders, spheres) | Core | `editors/mesh`, `bmesh`, `geometry`, BKE mesh | Need allocation, topology, attributes, export buffers |
| Object transforms and basic object hierarchy | Core | DNA Object, BKE Object/Scene/Collection, editors transform | Need minimal object+scene context; cannot equate an editable BMesh with full scene |
| Vertex, edge, face selection and Edit Mode | Core | `bmesh`, `editors/mesh`, `editors/transform` | Browser input/selection replacement; preserve topology semantics |
| Extrude, inset, bevel, loop cut, dissolve, merge | Core target | BMesh operators and tools, geometry, mesh editor | Validate operations separately; many editor wrappers depend on WM/RNA/context |
| Mesh normals and triangulation | Core | `blenkernel`, BLI, BMesh, geometry | Distinguish editable n-gon data from GPU triangle representation |
| Undo/redo | Core target | editor undo, `windowmanager`, BMesh backup, BKE | A lightweight replacement may be needed |
| UV editing, texture coordinates | Core target | BMesh custom data, BKE mesh/attributes, UV editor, image buffers | Scope of unwrap and texture painting is still open |
| Basic material/texture preview | Core target | BKE materials/images, image buffers, GPU/Draw | Could be replaced at the presentation layer |
| Import/export and save | Core target | `io`, `blenloader`, BKE, DNA | Native `.blend` compatibility vs custom project format is not yet decided |
| Full Cycles/path-traced rendering | Defer / not initial product | `intern/cycles`, `render` | Removing from a build differs from deleting every referenced library |
| Animation, rigs and timeline | Defer / not initial product | `animrig`, actions, sequencer, editors | Some data types remain transitive dependencies |
| Rigid body/fluid/simulation | Defer / not initial product | simulation, rigidbody, mantaflow, modifiers | Check which geometry algorithms depend on optional libraries |
| Video editing/compositing | Defer / not initial product | sequencer/compositor | Shader and image code might remain shared |
| Geometry Nodes and non-destructive modifiers | Product decision pending | nodes, modifiers, functions, depsgraph, geometry | Heavy dependency surface; may follow minimal direct editing |
| Sculpting, Python scripting, addons, advanced painting | Product decision pending | sculpt editors, python, paint | Not assumed removable without mapping use cases |

This mapping defines the **features to investigate**, not a promise that they have been implemented or successfully extracted.

## 3. Architectural boundaries

### 3.1 Data: DNA -> BKE -> editable BMesh

Blender's persistent data structures include `Mesh`, `Object`, `Scene` and related identifiers; their definitions are in DNA headers, including:

- `source/blender/makesdna/DNA_mesh_types.h`
- `source/blender/makesdna/DNA_object_types.h`
- `source/blender/makesdna/DNA_scene_types.h`

BKE implements their creation, ownership, modification, attributes and runtime state. Relevant files include `blenkernel/intern/mesh.cc`, `BKE_mesh.hh`, `BKE_attribute.hh`, `BKE_customdata.hh` and `blenkernel/intern/editmesh.cc`.

BMesh is the editable, connected topology representation. Its foundational types are `BMVert`, `BMEdge`, `BMLoop`, `BMFace` and `BMesh`, declared in `source/blender/bmesh/bmesh_class.hh`. They differ from the persistent `Mesh` representation.

The conversion bridge is `bmesh/intern/bmesh_mesh_convert.cc`: `BM_mesh_bm_from_me` for Mesh -> BMesh and `BM_mesh_bm_to_me` for BMesh -> Mesh. The conversion source also handles custom data, shape keys and multiresolution-related concerns; a minimal port should not assume this file can be reused without those dependencies.

### 3.2 Commands: Python/UI -> WM operators -> editor -> BMesh

Concrete primitive flow from inspected source:

1. `scripts/startup/bl_ui/space_view3d.py` creates a `mesh.primitive_cube_add` menu command.
2. `source/blender/editors/mesh/mesh_ops.cc` registers `MESH_OT_primitive_cube_add` in the Window Manager's operator registry.
3. `source/blender/editors/mesh/editmesh_add.cc` implements `add_primitive_cube_exec` and hooks it to the operator.
4. The operation constructs the mesh through Blender's primitive/BMesh code and BKE/scene data paths.

Concrete edit flow:

1. `editors/mesh/editmesh_extrude.cc` uses `EDBM_op_init` to initialize BMesh operators such as `extrude_discrete_faces`.
2. BMesh runs topology algorithms; corresponding lower-level implementation is under `bmesh/operators/bmo_extrude.cc`.
3. `editors/mesh/editmesh_utils.cc` provides `EDBM_update`, which calls `DEG_id_tag_update(..., ID_RECALC_GEOMETRY)` and emits `WM_main_add_notifier(...)` to refresh dependent state.

Implication: the browser UI should call a narrow **modeling API**, not directly reproduce the full operator context and Window Manager just to extrude a face. This is a candidate architecture to validate, not proof of an already standalone BMesh runtime.

### 3.3 Evaluation: change tagging -> dependency graph -> evaluated results

`source/blender/depsgraph/intern/depsgraph_eval.cc` implements refresh/frame-change evaluation using dependency graph internals. The editor tags mesh geometry changes, and consumers can request updated evaluated data.

A simple direct-edit prototype might work with immediate mesh updates and no full dependency graph. The moment non-destructive modifiers, complex object relationships or other evaluated state are included, this assumption must be revisited.

### 3.4 Display: Draw -> GPU -> GHOST/native backend

The Workbench draw engine in `draw/engines/workbench/workbench_engine.cc` consumes mesh/edit-mesh and dependency graph data and makes GPU calls. The GPU module implements common buffers, shaders, contexts and backends. Its platform backends in this fork include `opengl`, `vulkan`, `metal` and a non-rendering `dummy`.

`source/blender/gpu/intern/gpu_context.cc` includes GHOST context/system interfaces. GHOST chooses native OS implementations (Win32, Cocoa, X11, Wayland or SDL), plus a headless option.

For a web MVP, a browser renderer fed by engine vertex/index buffers avoids the up-front cost of porting the full Blender Draw/GPU/GHOST stack. A true Blender GPU WebGPU backend is a separate, larger architectural project.

### 3.5 Files: Window Manager -> Blender Loader -> DNA data

`source/blender/windowmanager/intern/wm_files.cc` calls `BLO_write_file`. The Blender Loader implementation in `blenloader/intern/writefile.cc` handles persistent `.blend` file writing, involving Blender's data model and structured file format.

Decision needed later: support full `.blend` compatibility, an intermediary export (e.g., glTF/OBJ), or a deliberately smaller native web project format. Do not assume serialization can be solved by saving GPU buffers.

## 4. Proposed architecture boundaries for portability

```text
Browser UI (panels, tools, menus, keyboard, pointer, files)
       |
Browser interaction and command adapter (JS/TS)
       |
Stable WASM C ABI / typed bridge
       |
Selected Blender-derived geometry engine
  BLI math + memory
  BKE Mesh/attributes (required subset)
  BMesh topology + selected operators
  Geometry algorithms (required subset)
       |
Mesh snapshots / vertex, index, UV, material attributes
       |
Web viewport renderer (WebGL2 or WebGPU; decide in Phase 1.3)
```

This is an **architectural hypothesis**. Phase 1.2 must identify the real source dependency closure; Phase 1.3 must prove an actual Emscripten build.

### State and ownership questions to resolve

- Are persistent Mesh and BMesh both retained throughout editing, or are snapshots converted on tool completion?
- Which object/scene/selection semantics are kept from BKE vs implemented at the browser/application layer?
- How are identity, vertex/face selection and topology indices preserved across operations?
- How are normals, UVs and material slots generated and invalidated after topology changes?
- How will undo/redo avoid invalid stale memory handles across the JavaScript/WASM boundary?
- Which data format preserves editing semantics between sessions?
- How does the browser handle memory growth, workers/threads and large models?

## 5. Dependency observations from the initial architecture audit

- BKE links BMesh, Depsgraph, GPU, Draw, GHOST, Nodes, Modifiers, Render, Sequencer and more at the CMake target level.
- BMesh links BKE, BLI, DNA, Depsgraph and supporting dependencies.
- Geometry links BKE, BMesh, BLI, DNA, Functions and Nodes.
- GPU links BKE, BMesh, Draw, Nodes and image processing, plus conditional native backends.
- GHOST links BLI, DNA, GPU and Image Buffers; native windowing selection is conditional.
- Blender's build utility `build_files/cmake/macros.cmake` explicitly sets `LINK_INTERFACE_MULTIPLICITY 3` to accommodate longer library dependency loops.

**These are target-level edges, not proven necessary runtime dependencies of each modeling feature.** Detailed closure, cycle analysis and removal criteria move to Phase 1.2.

## 7. Phase 1.2 handoff — exact investigations

1. Enumerate direct target edges and mark `PUBLIC`, `PRIVATE`, conditional and platform-specific links.
2. Compute and review strongly connected target groups (BKE/BMesh, Nodes/Geometry, GPU/Draw and connected subsystems).
3. Build a **source-level** dependency closure beginning with one primitive constructor and one BMesh editing operation, not all Blender code.
4. Inventory DNA/RNA/generated headers and startup requirements; distinguish build-time from runtime dependencies.
5. Inventory external libraries and determine which selected source files truly use them.
6. Record platform-specific system calls and threading assumptions.
7. Produce candidate reduced CMake targets for an isolated native prototype; 1.3 will test them.
