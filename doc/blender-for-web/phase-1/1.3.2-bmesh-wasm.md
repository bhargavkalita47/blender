## 2. What is genuinely compiled

### Topology algorithm

The test links unchanged `source/blender/bmesh/intern/bmesh_structure.cc` with `tools/blender_web/wasm/bmesh_disk_bridge.cc`.

Blender owns the disk-cycle routines: edge insertion, removal, validation, count and vertex replacement. The test bridge creates temporary `BMVert` / `BMEdge` storage, passes it into the **original algorithms**, and returns numeric results over a narrow C ABI. There is no alternative edge connectivity implementation in JavaScript.

This intentionally tests topology primitives, not a persistent `BMesh` owned by `BM_mesh_create`. The latter uses memory pools and CustomData, so it was tested separately.

### Empty BMesh allocation

The optional diagnostic links the real `bmesh_mesh.cc` with source from `intern/guardedalloc`, `source/blender/blenlib/intern/BLI_mempool.cc`, `source/blender/blenkernel/intern/customdata.cc` and `intern/clog`.

The exported function runs Blender's original `BM_mesh_create` with the default allocation template and verifies all four element pools exist with zero vertices, edges, loops and faces.

**Lifetime caveat:** That allocation-only fixture intentionally leaves one mesh for process teardown. It is a **single-use feasibility experiment**, not an approved API and not proof of correct cleanup or leak-free repeated allocations. Do not expose it to a long-lived browser session.

## 3. Source portability finding and minimal fix

In the original fork, `source/blender/blenlib/BLI_resource_scope.hh` asserted:

```cpp
static_assert(sizeof(ResourceScope) == 16);
```

On wasm32 this fails because the class represents two pointer-sized members and pointers are 4 bytes. We changed it **only on the development branch** to:

```cpp
static_assert(sizeof(ResourceScope) == sizeof(void *) * 2);
```

The original native 64-bit check remains equivalent (`2 * 8 == 16`), while wasm32 checks `2 * 4 == 8`. This is a layout-assert portability correction, not an algorithm change. The CI includes a native Clang syntax/layout check and a wasm32 layout check; both must pass before merging.

The test harness also needed the include path `source/blender/blenloader_core` for `BLO_core_bhead.hh`. This is a build-script include adjustment, not a Blender core modification.

## 4. Self-review: encountered errors and fixes

1. **Incorrect test adapter declaration:** Initial adapter called private `bmesh_disk_count` without a declaration. Fixed via a narrow **test-only forward declaration**. Original BMesh source unchanged; subsequent real WASM runtime test passed.
2. **Unresolved allocator and BKE symbols:** An attempt to link `BM_mesh_create/free` with only `bmesh_mesh.cc` failed as expected. Expanded probe compiles original GuardedAlloc, BLI mempool and BKE CustomData sources.
3. **32-bit ResourceScope assumption:** BKE CustomData initially failed compile due hard-coded `sizeof(ResourceScope)==16`. Replaced with pointer-size assertion, then CustomData compiled.
4. **Missing Blender Loader include path:** Added `blenloader_core` to probe header search paths.
5. **Selection data enum issue:** `bmesh_marking.cc` and `multires.cc` encounter narrowing of 128 into an enum backed by `char` under the WASM compiler configuration. **Not silently fixed with unsafe global flags.** Required before those source units can be part of the chosen runtime.
6. **Third-party formatting dependency:** `blenlib/intern/index_mask.cc` needs `fmt/format.h`, unavailable in the small Emscripten experiment. Must either supply the actual compatible fmt library/headers for WASM or isolate the relevant code.
7. **Diagnostic-script dependency coupling:** An unrelated candidate-source compile error could prevent the one-shot BMesh constructor test from running. Changed the script to compile `bmesh_mesh.cc` separately and record optional link failures independently.
8. **Incorrect interpretation risk:** Link probes intentionally capture failure without marking the baseline WASM compile/runtime test as failed. The JSON status files report distinct results.

## 5. Remaining link closure for proper destruction

The original `BM_mesh_free` source references cleanup via:

- BMesh iterators and `BMO_error_clear`.
- `CustomData_bmesh_has_free`, `CustomData_bmesh_free_block`, `CustomData_free`.
- `BLI_mempool_destroy`, guarded allocator and Python-handle invalidation.
- BKE loop-normal cleanup (`BKE_lnor_spacearr_free`).
- Additional BKE helpers reached by CustomData: multiresolution displacement, CustomData-file I/O, math interpolation, index masks, logging, listbase and other code.

Some new source providers compile under Emscripten; others are blocked by `fmt` and signed-`char` enum limitations. The workflow records `lifecycle-expanded-status.json` and `lifecycle-full-link.log`; only a genuine successful link and runtime check can close this gate.

## 6. Reproduce tests

With a full checkout of the branch and activated Emscripten 4.0.12:

```sh

# The passing topology test is also runnable directly after the build:
node tools/blender_web/wasm/verify-bmesh-disk.mjs build/blender_web/bmesh_wasm

# One-shot empty-BMesh test (only if bmesh_alloc.wasm linked):
node tools/blender_web/wasm/verify-bmesh-allocation.mjs build/blender_web/bmesh_wasm
```

Review `build/blender_web/bmesh_wasm/status.json`, `lifecycle-expanded-status.json`, and `allocation-probe-status.json` separately.
