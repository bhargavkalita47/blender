# Phase 1.3.2 — Blender BMesh editing in WebAssembly

**Status: PASS (Node-hosted WASM); ready for integration.**
**Source:** Blender 5.4 Alpha pinned at `67e5a5f874cf37e2a114cebd24f219d8c44a16ad`.
**Toolchain:** Emscripten 4.0.12, Node 22.23.4, Ubuntu GitHub Actions.
**Scope:** Genuine original Blender BMesh algorithms and allocators linked through a narrowly scoped C ABI. No replacement JavaScript topology engine.

The handle test runs 2,000 original BMO extrusions across 1,000 create/extrude/extrude/destroy cycles. It rejects invalid and stale handles, exercises 16 simultaneous mesh slots with capacity guard, validates face loops and radial adjacency after extrusion, and compares the original GuardedAlloc measured bytes before and after the warmed stress run (both 0 bytes in that run).

The compiled handle API WASM from the passing run is 108,463 bytes. That size describes this **small feasibility module**, not an entire modeling kernel.

## What executes

The linker includes original Blender `source/blender/bmesh`, selected `source/blender/blenkernel`, `source/blender/blenlib`, `intern/guardedalloc`, and `intern/clog` translation units. A thin C ABI bridge offers bounded cube creation, top-face extrusion, mesh destruction, topology counts, topology validation, opaque generation-checked handles and allocator counters.

We deliberately use the original Blender `BM_vert_create`, `BM_face_create_verts`, `BMO_op_init/exec/finish`, `BM_mesh_create` and `BM_mesh_free`. Blender's underlying BMesh topology ownership is not replaced with a JavaScript model.

## Failure investigation and correction

An earlier strict run https://github.com/bhargavkalita47/blender/actions/runs/42385656834 **failed** the lifecycle acceptance check even though the cube, extrusion and handle test probes passed. The lifecycle link command omitted the original BMesh topology objects that the passing cube and extrusion links included. The failure was not waived. The lifecycle command was corrected to link the same topology sources, rerun, and its own 1,000-cycle `BM_mesh_create/free` test passed in the successful run above.

## Portability and limitations

- The original source baseline is held in `main`; the WASM work is developed outside of `main`.
- The `BLI_resource_scope.hh` size assertion is now pointer-width aware; native and wasm32 checks pass.
- The probe uses `-funsigned-char` to represent Blender's 1-byte flag enum bit 7 and `FMT_HEADER_ONLY` for the selected compatible fmt headers. Serialized DNA compatibility and general edit-mode selection semantics have **not** been validated.
- The C ABI is a bounded feasibility fixture, not production scene management. Selection, UVs, arbitrary polygon triangulation, undo, materials, texturing and large-scene performance are outside this milestone.
- Node-hosted WASM execution is verified here; running in a real browser and copying geometry to JavaScript are Phase 1.3.3.
- Native full Blender CMake configuration and independently linked native reduced-core proof remain **blocked** by the missing compatible OpenColorIO 2.3.0 package. The isolated WASM success does not resolve that earlier build prerequisite.

## Reproduction

With Emscripten 4.0.12 active and compatible `fmt` headers installed:

```sh
bash tools/blender_web/wasm/build-bmesh-objects.sh
node tools/blender_web/wasm/verify-bmesh-lifecycle.mjs build/blender_web/bmesh_wasm
node tools/blender_web/wasm/verify-bmesh-cube.mjs build/blender_web/bmesh_wasm
node tools/blender_web/wasm/verify-bmesh-extrude.mjs build/blender_web/bmesh_wasm
node tools/blender_web/wasm/verify-bmesh-handles.mjs build/blender_web/bmesh_wasm
```

**Milestone decision:** Phase 1.3.2 PASSED all its defined source/runtime/memory/topology gates. Phase 1.3 as a whole still requires browser mesh transfer and browser/performance/compatibility verification.
